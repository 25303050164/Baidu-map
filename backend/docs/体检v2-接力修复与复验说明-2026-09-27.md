# 体检 v2 接力修复与复验说明

日期：2026-09-27。基于 `feat/facility-checkup-v2` 的本地工作区修改。
本记录描述本次修复，不追改历史快照、任务号、原始截图或 `resultHash`。

## 1. 本次修复

### 路线核验传输

`OnlineRouteTransport.route` 的参数是剩余秒数，而底层 `BaiduProvider` 接收单调时钟绝对截止时间。
现转换为 `time.monotonic() + timeout`；取得服务池发送位置后重新计算剩余时间，不延长任务期限。
内部 `baidu_place:<uid>` 转为百度原始 UID，其他来源仅发送目标坐标，不伪造百度 UID。

截止、HTTP 失败等观测明确设置 `endpoint_verified=False`；核验记录也从实际端点解析结果取值。
新增测试通过 `httpx.MockTransport` 驱动生产 Session、Provider 和核验阶段，检查实际请求被发送、
UID、HTTP 超时参数、距离、时长、端点及严格结论。只在 HTTP 边界替换网络，不使用合成路线适配器绕过生产代码。

### 服务池等待与记账

服务池先取得同一服务的在途锁，再等待响应间隔；上一条响应的限流冷却不会被排队者绕过。
等待锁也受截止时间约束。预算检查与实际扣除分开，排队截止不扣任务或日额度；
发送前才预留，发送后的失败和不确定请求继续保守记账。加入排队超时与并发冷却回归。
这些数值仍是本应用调度计数，不能代替百度实际账单。

### 连续设施密度热力

v2 使用既有 `createDensityOverlay` 在地图覆盖物容器中绘制 Canvas。
输入为设施图层接收的圈内设施，按 UID 去重、等权计算，核半径 120 米，固定色阶 0–4 个/公顷；
以同修订计算圈面裁剪，保留孔洞。没有设施或圈面时不补造热点。

独立开关“设施密度热力”默认开启；“模型网格采样”保留路网估计距离，明确不属于百度实测。
关闭点位或圈面显示不会阻止热力加载依赖。密度开关不再重建无关面与点覆盖物。
Canvas 原点及裁剪路径统一到覆盖物像素坐标，适应非零原点、平移、缩放及高像素比。

浏览器测试检查的是专属 `facility-density-canvas` 的实际非透明像素、孔洞及圈外透明、
开关恢复和视角事件；不能以底图 Canvas 存在或聚合点数量代替热力验收。

### 核验与模型的解释

`checked` 表示已尝试的设施数，`failed` 表示未得到严格 POI 结论的数量，`unresolved` 是模型入口未确认数。
界面按这一语义表述，不将失败说成超出 1000 米。

删除了不成立的网格冲突比较：中心→某设施，与该设施所在网格→最近同类设施，是不同的起终点问题。
旧实现还混用了中心局部格号和 `EPSG:32651` 全局格号。当前返回 `modelCell/modelStatus=null`、
`conflict=false`、`modelComparison=not_comparable_origin_and_destination`，并明确提示未作网格冲突判定。
该结果表示“未比较”，不表示模型已与实测一致。

核验点着色读取实际 `poiStatus`；模型网格点 ID 包含类别，避免同一格的不同类别相互覆盖。

### 可达性评估性能

首次报告回归触发 120 秒测试等待超时，任务仍在 `accessibility`。
对同一合成路网与已保存的设施修订做 cProfile：总耗时 148.10 秒（含剖析开销），
`attach_point` 45,675 次、累计 93.99 秒，说明跨类别重复接入是主要成本。

新增 `PointAttachments`，在一次评估的各类别与相邻网格间共享。以精确米制坐标作为键，不四舍五入；
保留 50 米限制，缓存失败结果，最多保留 50,000 个坐标。缓存绑定同一 GraphStore，跨图使用直接拒绝，
任务结束后释放，不使用跨任务全局缓存。达到上限仍正常计算，不丢支持点。

回归对缓存启用与禁用的完整评估结果逐字段比较：覆盖、灰区、热力与评分一致；
该测试样例的接入次数减少超过 50%。50 米与 50 米加微小偏移分别判定，证明缓存没有放宽接入标准。
报告整链路随后 8 项全部通过，未修改原有 120 秒等待上限。
以上为本机合成样例结果，不推断真实社区的固定耗时或整体加速比例。

## 3. 后续验收与开发门槛

### P1：重新取得真实链路证据

1. 在没有在途任务时启动修复后的后端；已运行且未开启 reload 的旧进程不会自动使用本次代码。
2. 核对本地 AK 权限、来源限制、额度与配置，AK 不写入报告、日志或版本库。
3. 运行 `npm run test:checkup-live`，两个引擎均用国定一社区、400 档；该命令会使用真实额度。
4. 保存每个任务的五版修订、快照、全部图层、报告、热力截图和核验审计；逐项核对任务号与哈希。
5. 分开统计 HTTP 返回路线、道路端点证据、严格 POI 可达、严格 POI 超标准、pending。
   有道路路线不等于严格 POI 映射成立。不能为了得到绿灯放宽端点判定或把未知当不可达。
6. 如样例没有可达或超标准的严格样本，应补独立可验证样例；保留缺样本结论，不能宣称全项验收。

### P1：可比较的灰区重点核验

以评估域内的真实支持点为路线起点，保存 BD09LL、米制坐标、CRS、父子格 ID、设施 UID、入口身份、
路网版本及规则版本。模型和百度路线必须绑定同一对起终点。
一次可达路线只能证明该点的存在性；某一家超标不能证明整类设施不存在。
证明缺口需有候选集完整性或可解释的排除证据。冲突只触发细化与新修订，不覆盖已冻结面积。
回归至少涵盖相同设施不同起点、多设施更近替代、跨河/门禁、端点偏移、25 米子格及预算耗尽。

### P1：目录与入口证据

当前 `catalogCompleteness=unverified` 继续保留。
优先审计原样例隔离记录：分类词命中、UID 冲突、范围排除、分页覆盖与样本时间分别统计。
人工复核后更新分类规则版本，用固定脱敏样例回放比较接收/隔离变化，避免为了提高覆盖率直接放宽分类。
导航点与实际入口不能自动等价；需要入口来源及合法连接证据才能提升证据等级。

### P2：统一配额与性能

成圈仍走旧共享闸门，未全部纳入新服务账本；direction 也未设置日预算。
迁移时两个引擎共用 direction 调度器，移除内层重复限流，区分本地计算、缓存、发送预留与响应确认。
并发验收应覆盖双引擎、详情点击、超时重试、跨配额降档时刻及取消。
日预算应依据账号实际权限与应用分配确定，不能从 QPS 反推每日额度。
性能比较需固定路网、边界、规则和数据版本，验证优化前后 C/G/U 面积、灰区和采样值相同。
