## 二、改了什么，以及预算/缓存怎么计量

### 幂等先于预算（`checkups/manager.py`、`checkups/store.py`）

`submit_extension()` 现在是：认领资源（任务 404/圈面 409）→ **按 `(taskId, clientRequestId)` 找已有请求** →
命中且参数等价则立即返回原记录（不读修订计算、不入队、不发请求、不扣额度）；参数不同则 409，
且这个判断在余额检查之前。只有确认为新请求才做首轮计划与预算检查。

请求身份 = 客户端声明的那两件事（类别集合 + 是否显式给出预算），冻结在新列 `intent` 里：

- 省略预算的重试永远与"当初也省略"的那一行相同，默认值、几何或余额变化都不影响它；
- "省略"与"显式写出当时的默认值"仍互相等价（保留基准版本的语义），但"显式写了别的数"是另一个请求；
- 旧版本写下的行（`intent` 为 NULL）仍按它被创建时的规则判定：用本次解析出的预算与冻结的 `budget` 比较；
- 数据库 `UNIQUE(task_id, client_request_id)` + `BEGIN IMMEDIATE` + `created` 标志仍然是唯一的创建点，
  竞态落败的一方只取回那一行、不入队。

### 预检看得见缓存（`poi/plan.py`、`checkups/facilities.py`、`checkups/manager.py`）

新增 `poi/plan.py`：用**规划器自己的**第一轮（同一份 `coarse_blocks`、同一套轮转、同一批主关键词）
加上 `poi/cache.page_key` 的真实页键，产出 `InitialPage`/`InitialPlan`；`reusable_pages()` 只用
`KeyedCache.get()` 做只读查询（不 build、不刷新 `obtainedAt`、不加入 in-flight 请求）。
`estimate()` 给出契约里的五个量：`initialPageCount`、`reusableInitialPageCount`、
`estimatedNewInitialCalls`、`remainingTaskBudget`、`remainingDailyBudget`。

判定规则（补查与设施阶段共用 `budget_refusal()`）：

- 预计新增调用为 0 → 不拒绝（缓存可满足，零余额也放行）；
- 部分可复用 → 不拒绝，按缺页执行（已付过钱的页面是证据，实际派发仍由池子兜底）；
- 完全冷启动 → 保留必要拒绝（任务桶不足 422、日额度不足 429），并带全部数字；
- 预检不预留额度、不刷新缓存时间；派发前仍由 `ServicePool.attempt()` 做最终检查与原子扣减。

### 两把尺子（`poi/online.py`、`poi/cache.py`）

`OnlinePlanner` 现在接受显式 `RunLimits`：

- `processing_steps`（v2 为 `PROCESSING_STEP_LIMIT = 4096`）管**本地处理**：缓存重放、翻页、细分、重试；
  到顶的停止原因是 `processing_limit_reached`；
- **网络预算**仍只由任务桶与应用日账本管，在 `ServicePool.attempt()` 里原子扣减；失败、超时、重试都计入，不退款；
- 只有指名 `budget=` 的旧调用方保持原语义（页数上限 + 预算拒绝即停），由 `legacy_limits()` 固定，CLI 与旧接口不受影响。

计量是显式的：`CachedPages` 每页返回 `PageResponse(payload, reason, manner)`，
`manner ∈ {live, cache, shared, refused}` 由真正解决这次请求的那一层写出。规划器据此把
`network_calls` 只加在 `live` 上；`attempts`（= 处理过的页面数）与 `network_calls`（= 真正派发的新调用数）
是两个数。契约里 `requests`/`networkRequests` 的含义未改，另加 `statistics.processedPages`/`networkCalls`/
`processingLimit`/`allowanceRefusedPages` 便于核对。

余额用尽时的行为：`task_budget_exhausted`/`daily_budget_exhausted` 不再是整轮的致命错误，
而是**那一页**的结果；运行继续把缓存里能答的页面读完，缺页逐页记名，整轮停止原因报
`network_budget_exhausted`。上游 `quota`、持续 `rate_limit`、`permission` 等仍是致命停止（有界、保留已取页面）。
纯缓存流程也检查取消与 deadline（它绕过了配额池，不能被池子兜底）。

### 诊断与文案

- `facilities.initialPlan`（首轮估算，标注 `isReservation: false`）；
- 补查状态/结果新增 `stopReason` 与 `initialPlan`（定稿时冻结，随状态即可读，不必再取结果文件）；
- `/api/v2/capabilities`：新增 `poiPlanning`（`processingStepLimit`、两本账、首轮是估算），
  `cache.processLocal: true`，并把 `budgets.poiRequestsIsLowerBound` 改为 **false**、新增
  `poiFirstRoundIsAnEstimate: true`（`4 × 小类数` 是冷启动首轮估计，不是总请求数的下界）；
- 前端：补查面板显示预算/页面处理/新增网络/首轮估算/停止原因，余额下方显示处理上限与缓存口径；
  `requiredRequests` 更名 `estimatedFirstRoundPages`，文案改为"按最多 4 个查询分块估计的冷启动首轮页数……
  首轮够用不代表查完，命中缓存的页面不消耗网络额度"。**没有**新增任何按余额禁用补查的逻辑。

## 五、需要运营者核实与诊断的配置

1. **先看生效档位，再谈提高额度。** `/api/v2/capabilities` 的 `quota.tier` 报出当前是 `current` 还是
   `fallback`；切换时间（默认 `2026-09-30T00:00:00+08:00`）之后只提高 `BAIDU_PLACE_DAILY_BUDGET`
   **不会**有任何效果，要调的是 `BAIDU_FALLBACK_PLACE_DAILY_BUDGET`。本轮没有改动任何默认值或切换时间。
2. **四种限制互相独立**：QPS/并发上限、单任务预算（`facilities.maxPoiRequests`，默认 60、上限 160）、
   应用日预算（本应用账本，按北京时间跨日、重启不清零）、百度账号真实配额（不在本账本里，
   必须按控制台授权核实）。`quota.claimsAccountBalance=false` 就是这句话的机器可读形式。
3. **估算是估算。** 分块数为 4、冷启动、只发主关键词时，核心三类首轮约 56 页、十类约 124 页；
   这只是首轮，翻页与细分还要更多，命中缓存的页面不消耗网络额度。前端与后端现在说的是同一件事。
4. **缓存是进程内存**：`cache.processLocal=true`、`freshnessSeconds` 默认为 null（只在同一任务内复用）。
   跨任务复用是部署的数据使用决定，本轮没有打开它，也没有把它写成"永久有效"或"重启后仍在"。
5. **诊断步骤**：`GET /api/v2/capabilities` 看档位/余额/缓存/处理上限 → 补查前后看
   `facility-extensions/{id}` 的 `requests`/`networkRequests`/`stopReason`/`initialPlan` →
   任务结果里看 `facilities.statistics`（`processedPages`、`networkCalls`、`allowanceRefusedPages`）
   与 `facilities.initialPlan`。预算拒绝的报文同时给出首轮页数、可复用页数、预计新增调用数与当前预算。

## 六、实现自查中发现并修掉的两处问题

初版实现完成后逐条复核时发现两处，都已修掉并补了断言（不是"顺便改改"，是这两条规则本身的要求）：

1. **等价规则写反了一半。** "省略预算"应当只在"省略解析出来正好等于它显式写的那个数"时命中已有行；
   初版把条件写成 `declared_then == record.budget`，对**显式**写了预算的行恒为真，等于把省略变成了
   通配符（一次 160 的补查会被当成 60 的重复提交）。现改为 `resolved_budget == declared_then`，
   并在 `test_extension_identity_is_what_the_client_declared` 里补了"显式 160 的行 + 省略（默认 160 / 60）"
   这两个方向。
2. **派发后失败被记成"没发出去"。** 超时/网络错误只可能发生在配额池扣减**之后**，
   初版把它们归为 `refused`，会让 `networkCalls` 比账本少算一次。现归为 `live`，
   并补断言：`test_a_dispatched_but_failed_call_is_still_a_new_network_call`（超时仍然计入新增调用）
   与 `test_a_refusal_before_dispatch_costs_nothing`（派发前拒绝一个都不算）。

另外顺手删掉了编辑过程中留下的一处同名 `_status_for` 重复定义（两处函数体逐字相同，第二处遮蔽第一处）。

## 七、追加验证：同一个地理位置的再次请求，60 次预算下会怎样

§三那组数字说明的是"缓存重放不再被 60 页截断"，它**没有**说明"同一个位置再请求一次就能查完"。
这两件事必须分开读，所以补做了下面这组对照（固定坐标 `121.513925, 31.313079`，核心三类，
每次显式 `maxPoiRequests=60`，密集合成数据整轮需要 **112 页** = 56 个首轮页 + 56 个第二页）：

| 场景 | 本次新增调用 | 成功取得页面 | 结果 |
| --- | ---: | ---: | --- |
| 默认档位（fallback，日额度 80），首次体检 | 60 | 60 | `partial`，`stopReason=network_budget_exhausted` |
| 默认档位，**同位置新建体检**（新请求标识） | 0 | 0 | 设施阶段被拒：`首轮需要 56 页…缓存可复用 0 页…本应用今天还剩 20 次`；任务本身仍 `completed` |
| 默认档位，**原任务新补查** | 20 | 80 | `partial`，日额度归零 |
| 默认档位，同一天余额 0 再补查 | 0 | 80 | `partial`，预检放行（首轮 56 页都可复用）但缺页一页也发不出去 |
| 默认档位，**跨日**后再补查 | 32 | **112** | `completed`（北京时间跨日，日账本按新日期从零开始） |
| 日额度充足（current 档），同位置新建体检 | 60 | 60 | `partial`：默认不跨任务复用，重新花一次额度 |
| 日额度充足 + 开跨任务窗口（`CACHE_FRESHNESS_SECONDS=3600`），同位置新建体检 | 52 | **112** | `completed` |
| 首轮页面全在有效缓存里，原任务补查 | 0 | 56 | `completed`，账本不变 |
| 同一请求标识重复提交（首次是 `partial`） | 0 | 60 | 取回原任务，报告逐字不变；要接着查必须用新标识 |

结论与判读规则：

1. **任务 `completed` 不等于设施查完。** 上面第二行就是实测：任务跑完了，`facilitiesStatus` 是
   `failed`、`facilities` 为 null，具名原因在 warnings 里。是否查完一律读设施侧的
   `facilitiesStatus` / `facilities.queryStatus` / `stopReason`。
2. **同位置 ≠ 同任务。** 页面缓存按任务归属，默认没有跨任务窗口，所以**重新体检**一页也复用不到；
   能接着上一次的进度、把额度花在缺页上的路径是**原任务的补查**（新补查标识）。这不是缓存失效，
   而是部署的取舍：跨任务复用由 `CACHE_FRESHNESS_SECONDS` 打开，那是数据使用决定，本轮没有默认开启。
3. **112 个未缓存页面确实超过一次 60 次预算。** 这是正常限制，不能靠加大默认额度或把 `partial`
   当完成来消除；重复触发同一请求标识也不会续跑（终态 `partial` 要接着查就用新补查标识）。
4. 按"最快能做什么"排序的处置：① 要走通"同位置接着查"，用原任务补查（不改任何配置）；② 要让
   **重新体检**也复用上一次的页面，需要运营者决定是否开启跨任务窗口；③ 每次 60、当日 80 装不下
   整轮 112 页，若业务要求一次查完，须按核实到的真实授权提高部署额度 —— 这三件事都不该由补丁
   擅自决定。

以上对照已固化为回归测试（同一位置、显式 60 次预算，断言设施状态、成功页数、实际派发与账本增量，
并断言补查前后原报告逐字不变）：`test_the_same_coordinates_in_a_new_task_do_not_reuse_the_first_tasks_pages`、
`test_each_extension_advances_only_as_far_as_the_days_balance_allows`、
`test_a_fully_cached_retrieval_at_the_same_budget_costs_no_new_calls`、
`test_replaying_a_checkup_request_id_never_starts_a_second_retrieval`、
`test_cross_task_reuse_is_the_deployment_option_that_lets_a_new_task_continue`。
全部使用合成 provider、临时 SQLite 与受控时钟（档位、跨日、缓存有效期都读同一个固定时钟），
`conftest.py` 的全会话外连防护为 0 次尝试。

## 八、仍不支持的能力

- **没有持久化断点续查**：页面缓存是进程内存，重启即失效；`partial` 是终态，服务不会自动跨日恢复、
  也不会自动续跑。后续若要做，需要持久化"成功页面 + 未完成队列"，并同时处理数据使用许可、有效期、
  查询计划/规则版本、圈面修订、页码与细分状态、幂等与重复扣费；不能只存一个"已用次数"。
- **没有跨进程共享缓存、没有分布式限流、没有多 AK 轮换**：并发与账本仍以单进程 + SQLite 账本为准。
- **没有真实浏览器端到端验证**（本机无 Edge）；也没有运行任何真实百度验收脚本。
- 补查仍然只查本次明确选择的类别、不重新成圈、不请求步行路线、不修改原任务的修订/报告/评分/灰区。
