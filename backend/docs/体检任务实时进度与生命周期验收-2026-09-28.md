# 体检任务实时进度与生命周期验收（2026-09-28）

本次让运行中的体检任务持续显示真实进度，并在真实 BMapGL 底图上补齐任务生命周期的各个场景。
验收使用可控的长任务后端，**不花任何百度服务额度**。

- Playwright 生命周期验收：**3 passed**（10.7 分钟）。
- 后端全量：959 passed、1 skipped。
- 前端：409 passed，`tsc -b` 通过。

截图与 `summary.json` 见 [assets/checkup-lifecycle-20260928/](assets/checkup-lifecycle-20260928/)。
`summary.json` 不含 URL 与 AK。

## 结论

- **已用时**：此前运行中的任务已用时恒为 0，原因是时钟混用，已修复（见"一"）。
  现在已用时按服务端墙钟计算，页面每秒递增。切页、刷新之后仍接着走，不归零。
- **阶段内进展**：后端在同一阶段内也发布实际进展。进展包括当前步骤、从何时开始、已完成的计数与上限，
  以及最近一次活动时刻。只报已经发生的事，**不给完成百分比**，也不预估剩余时间。
  首次载入城市路网（本机约 13.5 分钟）也逐 2 万条边报一次。
- **三种状态**：前端区分"正在计算或等待""连接中断，正在自动重连""疑似停滞：后端很久没有新进展"，
  并给出对应提示。此外还有"正在提交""正在核对上次的任务""排队中""正在取消"。
  界面上没有循环动画，也没有虚构的百分比。
- **状态接口的应答**：同一阶段长时间运行时，状态接口一直能应答。
  改造前，冷启动的 OSM＋百度任务曾让状态接口 83.8 秒、111 秒才回，甚至 120 秒超时。
  改造后，本轮验收中事件循环没有一次被占住超过 1 秒。
  真实首次载入路网的 13.5 分钟里，就绪与任务状态查询都在 0.43 秒内应答（进程刚启动后的第一次除外，见"二"）。
- **全程计数**：4 个任务，后端各只收到一次创建，没有重复任务。
  两次取消是同一个取消在刷新后补发一次，取消本身是幂等的。
  出进程的连接为 **0**，不消耗额度。

## 一、后端：运行时长的时钟混用

旧的 `CheckupManager.view()` 这样计算运行中任务的已用时：

```python
end = record.finished_at if record.finished_at is not None else time.monotonic()
elapsed = max(0.0, end - record.started_at)
```

`started_at` 存的是墙钟 `time.time()`（约 1.79×10⁹），`time.monotonic()` 是开机以来的秒数，两者相减为负数。
被 `max(0, …)` 截成 0，于是任务一直在跑，已用时却恒为 0。

现在所有存储的时刻都是墙钟，运行中的任务也按墙钟度量（`manager.py` 的 `view()`）。
状态视图同时返回下列时刻，前端据此自己计时，不必每秒问一次后端：

- `serverTime`：这次回答时的服务端墙钟；
- `startedAt`、`stageStartedAt`；
- `lastActivityAt`：计数、步骤、修订、状态任何一项变化都会刷新；
- `progress`。

## 二、后端：阶段内进展（`progress`）

`backend/app/checkups/progress.py` 的 `StepReporter` 把各阶段的实际进展写进任务记录。每条进展包括：

- `step`、`label`：步骤代码与中文名；
- `since`：这一步从何时开始；
- `count`、`limit`、`unit`：已完成多少、上限多少、单位是什么。

规则：

- 只报已经发生的事：采样发出了几次、检索发了几页、判定了几格、核验了几家、处理了几条边。
- `limit` 是上限（预算、额度、候选名单），可能提前停下，所以前端写成"预算上限""本阶段上限""候选"，
  不写成"x / y"，免得被读成完成比例。只有路网的边数是确数，写成"共"。
- 没有单位的步骤（如"建立评估域""准备步行图"）没有可数的东西，`count` 一律为空。
  调用方顺手传来的 0 也会被丢掉：否则引擎在载入路网时快照里的"0 次采样"，会被读成一个不动的计数。
- 计数的单位按阶段区分：成圈为次采样，设施检索为次请求，服务覆盖评估为格，路线核验为家，
  载入路网为条边。网络尝试数另记在 `requests` 与 `networkRequests`，载入与准备步骤不算尝试。

### 首次载入城市路网：逐 2 万条边报一次

OSM＋百度引擎，以及两种引擎的服务覆盖评估，都要用本机的上海步行路网（721,276 条边）。
进程里第一次用到它时要载入，本机实测约 13.5 分钟。
此前这一步只有开始那一下，前端只能靠"不报计数步骤"的 15 分钟阈值兜着，离误报"疑似停滞"只差一点。
现在拆成四步，前两种按边计数：

| 步骤 | 说明 | 计数 | 本机实测 |
| --- | --- | --- | --- |
| `graph_read` 读入路网文件 | 283 MB gzip JSON | 无 | < 10 秒 |
| `graph_build` 建立路网 | 解析每条边的几何 | 每 2 万条边 | 约 80 秒 |
| `graph_check` 校验边的几何与耗时 | 逐条校验方向、长度、步行耗时 | 每 2 万条边 | 约 11.7 分钟 |
| `graph_index` 建立空间索引 | 边索引与 STRtree | 无 | 约 10 秒 |

- **来源**：`LazyOsmOfflineEngine.loading` 记着载入到哪一步。
- **谁在等**：等路网的调用方都通过 `lazy.resolve()` 等待。可能是预热线程，也可能是前一个任务，还可能是本任务的成圈或评估。
  `resolve()` 每秒看一眼 `loading`，有变化就报给本任务的进展。
- **不算尝试**：这些步骤走 `EngineContext.step` / `on_step`，不改动任务的请求计数。
- **实测节奏**：计数每 15–20 秒前进一次，远在 90 秒的停滞阈值之内。

实测是可控后端刚启动时的一次冷载入：载入期间提交了一个 OSM＋百度任务，每 5 秒读一次它的状态。
读到的序列如下：

```text
17:00:42 running isochrone graph         –
17:00:47 running isochrone graph_check   300000 / 721276 条边   requests 0 / network 0
…（每 15–20 秒 +20000）
17:07:25 running isochrone graph_check   720000 / 721276 条边
17:07:31 running isochrone graph_index   –
17:07:37 running isochrone guidance      –          （冷启动约 1 分 50 秒）
17:09:25 running isochrone obstacles     –          （冷启动约 1 分 30 秒）
17:10:57 running isochrone sampling      42 / 200 次采样
17:11:41 running accessibility graph → views → category（174 格）
17:12:21 running reporting report
17:12:26 completed ready
```

这个任务从提交到完成共查询 131 次：

- 载入路网期间最长 0.42 秒；
- 整个任务最长 0.86 秒（进入服务覆盖评估时）；
- 汇总报告那一刻 1.18 秒（见"三"的冻结修订）。

同期还有每 10 秒一次的 `/control/ready` 查询，共 79 次。
除进程刚启动后的第一次（2.26 秒，首个请求的预热）外，都在 0.37 秒内应答。
单独测量读入与解析路网文件（0.7 秒＋3.3 秒）时，另一个线程最长只被挡 0.37 秒。
外部连接为 0。

profile 显示载入时间的 95% 花在 `GraphStore.__init__` 逐条边的 shapely 标量运算上（`oriented_geometry` 等）。
向量化这段校验能把首次载入缩短一个量级，列为后续工作。

## 三、状态接口在长任务中能否应答

状态接口和任务共用后端的事件循环。事件循环被占住，前端就问不到状态，只能显示"连接中断"。
可控后端里有一个事件循环看门狗：每 0.1 秒记一次心跳，两次心跳间隔超过 1 秒就记一次卡顿，并记下当时的调用栈。
它还记下每次第 2 代垃圾回收的耗时。

| 场景 | 改造前 | 改造后 |
| --- | --- | --- |
| 冷启动 OSM＋百度任务时的状态查询 | 120 秒超时；83.8 秒、111 秒才回 | 最长 0.63 秒 |
| 载入路网期间的第 2 代垃圾回收 | 9 次，各 0.58–2.99 秒，最后一次 6.34 秒 | 0 次 |
| 解析 283 MB 路网缓存 | `json.load` 独占 GIL 29 秒 | 期间的查询最长 0.83 秒 |
| 冷加载障碍层与风险层 | 2.94–7.14 秒 | 最长 0.79 秒 |
| 本轮 Playwright（4 个任务，含 OSM＋百度） | — | 事件循环卡顿（> 1 秒）0 次 |

原因与改法：

- **第 2 代回收遍历整张常驻路网**。一次完整的循环回收要走遍所有被跟踪的对象，全程持有 GIL。
  解析几百万个对象时它会被反复触发。
  `bulk_load.long_lived()` 的做法：载入前先回收一次，趁堆还小；载入期间不做完整回收；载入完把结果 `gc.freeze()`，挪出以后的每一次完整回收。
  路网、OSM 引导、障碍层、风险层的载入都包在里面。
- **C 版 JSON 解析一次持有 GIL 到底**。`bulk_load.loads()` 给 `json.loads` 挂一个 `object_hook`，每解析完一个对象回到 Python 一次。
  解释器借这个机会把 GIL 让给其他线程，解析时间只多一点点。
- **在事件循环上做的重活挪到工作线程**：
  - Hybrid 成圈的重建与候选排序；
  - 采样账本的整份重写（`persist()`）；
  - 路网的取用（`resolve()`）；
  - 引导与障碍层的载入。

本次还剩两处短暂占用，都在 1.5 秒以内，也都不是运行中长时间停留的地方：

- **建立空间索引**：首次载入路网结束时，约 1.4 秒（一次 C 调用，看门狗线程也拿不到 GIL）。每个进程只有一次。
- **冻结核验修订**：计算结果摘要 `canonical_hash`（C 版 `json.dumps`）约 1.4 秒，每个任务一次。
  C 编码器全程持有 GIL，挪到线程里也一样会卡住事件循环，所以没有改，记为已知限制。
  本轮 Playwright 中它没有超过 1 秒。

## 四、前端：实时状态（`life-circle-demo/src/checkup/live.ts`）

### 时钟与计时

所有"已用时""已持续""多久前"都按服务端墙钟计算：`serverNow = 上次回答的 serverTime + 本机从那时起走过的时间`。
本机时钟不准也不影响。页面每秒重算一次，两次轮询（1 秒一次）之间也在递增。

### 进度面板显示的内容

| 项目 | 内容 |
| --- | --- |
| 状态 | 状态标题与提示（见下表） |
| 任务 | 任务 ID |
| 最新修订 | 第 N 版 |
| 本任务已用 | N 次网络尝试：等时圈、设施与核验各池合计，只数真的发出的请求 |
| 已用时 | 排队时显示"尚未开始（已排队 N 秒）" |
| 当前阶段 | 阶段名，及本阶段已持续多久 |
| 当前步骤 | 步骤名、计数与上限，及本步已持续多久 |
| 最近一次成功连接 | 多久前 |
| 服务端最近活动 | 多久前 |

### 状态与提示

| 状态 | 何时 | 提示要点 |
| --- | --- | --- |
| 正在提交 | 创建请求已发出、回答未到 | 确认之前刷新，会按请求标识找回同一个任务，不会重复提交 |
| 正在向后端核对上次的任务 | 刷新或重开页面后 | 按保存的任务标识查询；核对期间不提交新任务 |
| 排队中 | 任务在排队 | 已排队多久；服务一次只执行一个任务（两个引擎共用） |
| 正在计算或等待 | 有进展，或沉默未超阈值 | 后端最近一次进展在多久前；不报计数的步骤另有说明 |
| 疑似停滞：后端很久没有新进展 | 连得上，但服务端沉默超过阈值 | 连接是好的；停在哪一步、多久；可继续等，也可取消重来（已发布的修订保留） |
| 连接中断，正在自动重连 | 请求失败（断网、连接被拒、超时） | 断了多久、连续失败次数、退避节奏（1、2、4、8、10 秒）、最近一次成功连接；任务在服务端照常进行，不会因断网被取消或重提 |
| 正在取消 | 已请求取消 | 后端会在当前步骤的下一个检查点停下；已发出的请求仍计入额度 |

"疑似停滞"的阈值：

- **报计数的步骤：90 秒**。每发一次请求、每判定一批格、每处理两万条边都算进展。
  最长的正常间隔是一次请求的超时（E8.2 单次 8 秒，最多 2 次），90 秒远大于它。
- **不报计数的步骤：15 分钟**。这类步骤只有开始那一下，例如读入路网文件、建立评估域、准备步行图、建立接入索引。
  冷启动时，OSM 引导约 2 分钟、障碍层约 1.5 分钟，都在 15 分钟以内。
- 连接中断时不对任务下任何判断：它可能照常在跑，也可能早已结束。

### 切页与刷新接回同一个任务

任务句柄存在 `localStorage` 里：请求标识、任务 ID、是否已请求取消。
**先存句柄再发创建请求**，所以请求发出后页面被关掉，刷新回来也能找回。

- 有任务 ID 就直接查状态。
- 没有任务 ID（创建的回答丢了或超时）就按请求标识查。这是只读查询，不会替用户重新提交。
- 句柄里记着"已请求取消"的，刷新后再发一次取消（幂等）。
- 在页面内切换"页面 × 算法"时，控制器不销毁，同一个任务接着显示。

## 五、可控长任务：`backend/tests/checkup_lifecycle_app.py`

可控后端只替换**出进程的那一层**，其余全是生产代码。

替换的部分：

- E8.2 成圈用解析解；OSM＋百度成圈用本机步行时间。
- 设施检索与路线核验走合成传输。它们照样经过生产的额度池、预算与截止时间，只是不出进程。
  所以界面上的"网络尝试"是这些模拟请求的计数，而出进程的连接为 0。

沿用生产的部分：

- 任务、修订、进度、取消、恢复、图层与报告，都是生产的那一套。
- 步行路网、障碍层、水系复核用本机真实数据，所以评估阶段的格数是真算出来的。
- 设施是合成的，所以结果里的覆盖率数值不作业务结论。

零额度靠两层保证：

- 进程以空的 `BAIDU_MAP_AK` 启动。
- 进程里装了套接字守卫：任何非回环地址的解析与连接一律拒绝并记数。
  每轮验收最后要求 `external.attempts == 0`。

控制接口：

- 停点：`create`、`isochrone`、`sampling`、`graph`、`places`、`assessment`、`routes`。
  可以"放过 N 次之后停住"，再按需放行。
- `pace`：每次经过都等一段时间，制造"同一阶段持续运行"。
- `/control/cold`：丢掉已缓存的障碍层与风险层。
- `/control/ready`：路网载完之前回 503，并带上载到哪一步、处理了多少条边。
- `/control/state`：停点、计数、任务、外部连接、事件循环卡顿。

启动方式见文件头与 `life-circle-demo/playwright.lifecycle.config.ts`。

## 六、验收场景与结果（`life-circle-demo/tests/checkup-lifecycle.spec.ts`）

真实 BMapGL（真实浏览器 AK，不花服务额度），msedge，1440×1000。
不录 Trace、视频，失败时也不自动截图。截图由用例自己挑时机，只截页面。

### 用例 1：E8.2 一个任务走完全程（3.1 分钟）

| 场景 | 做法 | 结果 |
| --- | --- | --- |
| 首次请求前 | 创建的回答压住；任务停在第一次采样之前 | "正在提交"（01）；回答到达之前刷新，按请求标识找回同一个任务；5 次读数都停在等时圈阶段，网络尝试 0，服务端最近活动的秒数在涨，最近一次成功连接一直是刚才（02） |
| 同一阶段持续运行 | 采样每 0.2 秒一次 | 连续 9 次读数，采样计数 0→3→7→12→16→20→20→25→29，单调递增；界面在 2.5 秒内跟上后端的计数（03） |
| 阶段切换 | 采样放开，停在设施检索第 3 页之前 | 后端切到设施检索后 **0.31 秒**界面跟上；计数 2、修订第 1 版都与后端一致（04） |
| 长时间无进展 | 停住不放 | 30 秒时仍是"正在计算或等待"；服务端沉默满 **90.5 秒**时变为"疑似停滞"，提示停在"检索设施"、连接正常、可取消（05）；放行后 **1.43 秒**回到"正在计算或等待"，计数继续上涨 |
| 断网 | `context.setOffline(true)` | "连接中断，正在自动重连"；连续失败次数 1→2→2→3→3→3→3→4→4，按退避节奏增长；后端这期间继续检索（06）；恢复网络后 **0.16 秒**接上，计数补齐 |
| 服务端不可达 | 在线但连接被拒 | 同样进入重连；恢复后 **1.89 秒**自己接上 |
| 切页、切算法 | 切到旧版页面再回来，切到 OSM＋百度再回来 | 回来还是同一个任务；切出去的 12 秒也算在已用时里（138.5 秒→150.7 秒） |
| 刷新 | `page.reload()` | 同一个任务、第 2 版修订；已用时 154.3 秒，不归零；仍显示"评估服务覆盖"（07） |
| 完成 | 全部放行 | 第 5 版；地图上的等时圈和"本次体检中心"都围着本任务的中心；报告也属于这个任务（08） |

计数：页面只发了一次创建，后端只收到一次创建，没有取消。

### 用例 2：创建超时与取消中恢复（36 秒）

- **创建超时**：创建的回答压过 15 秒的请求超时。页面按请求标识查到任务，没有发第二次创建，进入"正在计算或等待"。
- **正在取消**：一次检索请求停在半路时点"取消任务"，显示"正在取消"（09）。
  发出的请求收不回，后端要等它回来才走到下一个检查点，这期间已用时照走。
- **取消中刷新、切页**：仍是同一个任务、仍在取消。不重提，也不把取消中的任务当成"没有任务"。
- **放行**：停在"已取消"，地图区仍属于这个任务（10）。
- **计数**：创建 1 次。取消 2 次，其中第二次是刷新后按句柄补发的同一个取消。

### 用例 3：两个引擎、两个中心（6.9 分钟）

## 七、已知限制与后续

- **运行中的地图只画中心点**：结果在任务完成后按 `task.revision` 取回再画，面板上的"最新修订：第 N 版"表示已发布到哪一版。
  这是有意的：未完成的中间修订不在地图上冒充结果。
- **设施检索不能中途取消**：请求发出去就收不回，"正在取消"会持续到这次请求返回（单次上限约 8 秒，最多 2 次）。
- **不报计数的步骤**：OSM 引导、障碍层、评估域、步行图、接入索引只显示"已持续多久"，靠 15 分钟阈值判断。
  冷启动时它们各要 1–2 分钟，界面上只有时长在走，这是真实状态。
- **两处约 1.4 秒的事件循环占用**：建立空间索引、冻结核验修订的结果摘要，见"三"。
- **首次载入路网约 13.5 分钟**：大半花在逐条校验边。后续可向量化 `GraphStore` 的校验，这是缩短首次载入的主要方向。
- **旧接口**：旧版 `/api/v1/analysis/hybrid` 仍用原来的方式取用路网，不报载入进度。页面默认入口已是体检 v2。
