**任务**：`scheme.md` §6 C0
**执行时间**：2026-10-09
**证据级别**：**E1**（合成夹具、临时 SQLite、受控时钟、外连阻断；**没有**任何真实请求）
**入口**：`cd backend && .venv/bin/python -m tools.poi_query_benchmark --suite baseline --output ../.tmp/poi-benchmark`
**夹具**：`backend/tools/poi_benchmark_world.py`（世界与查询引擎）、`backend/tools/poi_query_benchmark.py`（计量与报告）、`backend/tools/poi_benchmark_guard.py`（外连阻断）
**结论一句话**：基线本身可复现地被量出来了 —— 核心三类在密集合成场景下要 **1379** 次真实派发才能查完，

## 1. 计量口径：数字是怎么来的

基准不是"理论页数"，而是穿过真实链路的实测量。每个场景复用：

| 环节 | 复用的生产代码 | 说明 |
| --- | --- | --- |
| 计划与首轮 | `app.poi.online.OnlinePlanner`、`poi/plan.initial_plan` | 与设施阶段同一套粗分块、轮转与首轮口径 |
| 页面键与缓存 | `poi/cache.page_key`、`app.cache.KeyedCache` | 真实页键；缓存命中不进入额度池 |
| 唯一扣费入口 | `quota.ServicePool.attempt()` | 每次派发一个预留；拒绝发生在发送之前 |
| 日账本 | `quota.DailyLedger`（临时 SQLite、受控时刻） | 每场景独立账本（见 §2） |
| 分页与截断 | `place_protocol.Pagination` | 不重写，不复制 |
| 结果处理 | `poi/normalize.normalize`、`classify`、`merge_entities`、`clip_to_domain` | 与报告使用同一套判类与归并 |

**计量恒等式（每次运行都断言，不成立即以非零码退出）**：

```text
真实派发 == 任务桶增量 == 日账本增量 == 会话自身的派发日志条数
处理页数 == 明细调度记录条数
live + cache + shared + refused == 处理页数
外连尝试 == 0
```

两次运行（12/13 个场景）中**全部成立**。

## 2. 夹具与它的边界

夹具是一个**受控世界**：确定性设施、稳定 UID，按（距离, UID）稳定排序分页，页大小 20。
名称与分类标签取自仓库自己的类别词典，因此判类走的是**真实分类器**，不是夹具查表。

夹具的建模假设（原样随每份报告输出）：

1. 每家设施只匹配一个检索关键词：本小类的主关键词，或本小类的一个额外关键词。
2. 一次查询返回"关键词落在提交集合内、且到查询圆心距离不超过所给半径"的设施，按（距离, UID）稳定排序。
3. `total` 是这批设施的真实条数；分页按同一顺序切片，页大小 20。
4. **结果里没有"这条命中哪个关键词"的字段**（官方响应结构也没有）。
5. 名称与分类标签取自仓库词典，判类走真实分类器。
6. 夹具**不**复制配额、限流、重试、截断、分页上限规则——这些仍由被测的生产代码决定。

几何：中心 `(116.405, 39.916)`，查询半径 `750` 米（2×2 粗分块，每块 750 米，外接半径 536 米）。
随机种子固定为 `20261009`。受控时刻 `2026-10-09T12:00:00+08:00`（决定日账本的"今天"与生效档位）。

**每场景一个独立账本**：受控时钟把所有场景钉在同一天，共用一个账本时前一个场景花掉的额度会把后一个
场景的冷启动首轮**拒掉**，那不是任何被测计划的属性。(首轮曾因此得到一排假的 `daily_budget_exhausted`，
已修正并重跑。)

**一条词典属性必须写在表前**：`training` 被词典标为 `negative`，凡判进它的设施都以 `negative:training`
**排除**，不进入计数。所以下面各表里"排除"一列包含它，而它是**词典决定**，不是检索失败。

### 3.3 次页与重试

`含重试页`（处理页数 − 首轮页数）随密度上升：稀疏 3、适中 147、密集 1098。
密集场景的绝大多数页数来自**翻页与细分**，不是首轮——这正是 `scheme.md` §6"不能只报减少了几个首轮请求"的实证。

### 3.4 十类密集（`dense-ten-majors-generous`）

十类共 31 个小类，首轮 = 4 × 31 = **124** 页；同一夹具、同一预算下整轮测得
**790 次派发、790 页、全部 124 个序列 `completed`、接收 8507 个 UID**（合法十类，无细分触发）。

> **这一行不能与上面的十四小类场景直接比较，原因在夹具而不在计划。**
> 本夹具的 `density_per_km2` 是**整个世界的**设施密度：设施总数固定，小类越多，每类的设施越少。
> 于是一个关键词在一个块内命中的条数会随小类数增加而下降——十四小类时每序列约 321 条（>150，触发截断与
> 细分），三十一小类时约 145 条（<150，不触发）。**"十类比三类便宜"是这个夹具的算术，不是真实世界的
> 结论。** 同一小类集合内部的场景（稀疏/适中/密集/默认 60/全缓存/各类上游故障）之间比较是有效的；
> 跨"小类数量"的横向比较无效，已列入 C2 的夹具改进项（密度应按小类给定，而不是按世界给定）。
>
> 该场景整轮耗时约 79 秒（含账本逐次提交），是 13 个场景中最慢的一项。

## 4. 这些数字说明了什么

**(a) 成本按"小类 × 分块 × 页"增长，而密集场景的页数由截断与细分主导。**
核心三类在密集夹具下需要 1379 次派发才 `completed`；默认预算 60 只能覆盖其中的 60 次，
拿到 1120 个接收 UID 后**正确地**报 `partial` / `network_budget_exhausted`，
并留下 56 个具名的 `task_budget_exhausted` 页面。没有任何一页被说成"这个区域没有设施"。

**(b) 十类冷启动在默认预算下**不能开始**，而且是具名拒绝。** 首轮需要 124 页 > 60，
准入规则返回 `budget_too_small`，**零派发、零账本增量**。这正是 A2 审计里那条"冷查询在预算不足时
应正确拒绝"的不变量在基准层面的复现。

**(c) 全缓存重放真的是免费的，而且证据不缩水。** `moderate-prefilled-zero` 在任务桶与日余额都为 0 时
处理了 203 页、**派发 0 次、账本 +0**，并报 `completed`，接收 UID 数 **1968**，与冷启动的
`moderate-generous` **完全相同**。这是本轮 A 阶段修复的核心性质（处理步数与网络额度是两把尺子），
现在有了整轮量级的证据：不仅"不花钱"，而且"结论一样"。

**(d) "无匹配"与"尚未确认"被分开，失败永远不会变成零。**

| 上游行为 | 结果 | 含义 |
| --- | --- | --- |
| 真实空目录（`total = 0`、空页） | `completed`，接收 0 | 这是"这里确实没有"，可以说 |
| 空页但 `total` 为正 | `partial`，56→280 个 `pagination_uncertain` 页 | 这是"还没确认"，不能说成没有 |
| 持续限流 | `failed` / `rate_limit`，**仅 2 次派发** | 有界重试后暂停 |
| 上游配额用尽 | `failed` / `quota`，**仅 1 次派发** | 停止性错误立即停 |
| 持续上游错误 / 首屏超时 | `failed`，**112 次派发** | 见 (e) |

**(e) 一处既有成本问题（本轮未改，按 `scheme.md` §12 记录而非"修掉"）。**
`upstream_error` 与 `timeout` 属于可重试错误，于是 4×14=56 个序列各自重试一次，
**112 次派发换来零条证据**。它不是本轮引入的，也不在 A 阶段授权范围内，
但它在本基准里是一个确定可复现的量级，应在 C/D 阶段一并评估（例如按序列进度而不是按错误类型决定是否继续）。

**(f) 截断与细分的联动是最大成本项。** `Pagination` 把 `total >= 150` 记为 `possible_truncation`，
该信号触发 `_subdivide()`，把一个块拆成 4 个再各查一遍。稀疏场景 1 页/序列即可完成，
密集场景每个序列要翻到上限并触发细分——这也解释了为什么 C1 审计把"合并会更早撞上 150 上限"
列为合并的**反例机制**而不是收益来源。

## 6. 本文件**不能**支持什么

- 不能支持任何**真实百度目录**的召回率或数量结论：计数基准是合成长方世界（E1），不是真实地物。
- 不能支持"合并查询能省多少"：那是 C2，且依 `scheme.md` §6 C2 只能给出"可试验/不可试验"。
- 不能支持真实接口的分页、排序、去重或截断行为：夹具的 150/20 口径来自 `Pagination` 的既有规则，
  而 C1 已确认官方文档的 150 条上限与之一致（但仍未验证 v3 的其它差异）。
- **夹具覆盖**（`fixtureCovered`）只在 `baseline-detail.json` 中作为诊断存在：
  它拿夹具自己生成的世界当真值，因此**不是**召回率，任何引用都必须与"相对基线召回"分开表述。
