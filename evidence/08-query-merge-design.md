# C1｜多关键词并集检索的可行性审计

**任务**：`scheme.md` §6 C1
**执行时间**：2026-10-09
**证据级别**：E0（静态代码/词典审计）＋ 官方接口文档原文；**没有任何真实请求**
**结论一句话**：按小类内部合并（同义关键词）在语义上是**可试验**的；跨类机械装箱**不可直接采用**，
而且现有响应校验器会**直接拒收**官方文档所述的多关键词页。

---

## 1. 本审计回答什么

`scheme.md` §6 C1 要求：梳理真实关键词、识别可无损合并的候选、确认并集返回能否把结果归属回原关键词、
审计多关键词分页、区分合并粒度，并检查与既有计划/缓存/评分机制的兼容性。

本文件只做这五件事，**不**给出收益承诺。§6 明确禁止把 `4 × ceil(14/10)=8`、`4 × ceil(31/10)=16`
这类极端理想化的首轮数字当作产品或上线收益指标。

## 3. 官方接口事实（原文引用）

来源：百度地图开放平台《地点检索 Web 服务 API》官方页面（服务端渲染的旧版 wiki，参数族与 v3 相同）：
<https://lbsyun.baidu.com/index.php?title=dev/webservice-placeapi>。
本文件引用的每句原文都在 2026-10-09 由本项目**本地重新抓取该页面后逐句核对**（页面正文 90,178 字节）。

| # | 事实 | 原文 |
| --- | --- | --- |
| F1 | `$` 并集检索、最多 10 个关键词 | `圆形区域检索和多边形区域内检索支持多个关键字并集检索，不同关键字间以$符号分隔，最多支持10个关键字检索。如:”银行$酒店”` |
| F2 | **并集页的每页条数按关键词数放大** | `多关键字检索时，返回的记录数为关键字个数*page_size。多关键词检索时，单页返回总数=关键词数量*page_size` |
| F3 | `total` 上限 150 | `POI检索总数，开发者请求中设置了page_num字段才会出现total字段。出于数据保护目的，单次请求total最多为150。` |
| F4 | 单次访问最多返回 150 条，且不可修改 | `出于数据保护目的，单次访问服务最多同时返回150条数据。此限制无法修改。请根据实际需求，通过添加分类、设置范围等方式，缩小检索范围。` |
| F5 | 分页参数 | `page_num 分页页码，默认为0,0代表第一页，1代表第二页，以此类推`；`page_size 单次召回POI数量，默认为10条记录，最大返回20条` |
| F6 | 半径默认是**加权**而非严格裁剪 | `radius 圆形区域检索半径，单位为米。（增加区域内数据召回权重，如需严格限制召回数据在检索半径范围内，请搭配使用radius_limit参数）` |
| F7 | `radius_limit` 会影响 total 准确性 | `设置为true时会影响返回结果中total准确性及每页召回poi数量，设置为false时可能会召回检索半径外的poi。` |
| F8 | 数据本身不是最新版 | `出于数据保护目的，地点检索服务使用的数据非最新版。` |

**F3/F7/F8 合起来说明一件事**：`total` 既被政策截顶、又受 `radius_limit` 影响、且目录本身不保证最新。
因此 `total` 只能用来判断"是否可能还没查完"，**不能**用来判断"这个区域到底有多少设施"。
现有代码已经按这个口径处理（`place_protocol.Pagination` 把 `total >= 150` 记为 `possible_truncation`），
本审计确认该阈值与 F3 一致，不是拍脑袋定的。

### 3.1 文档**没有**说的话（同样是结论）

- **没有**任何一句声称"多关键词一次查询 = 各关键词分别查完的结果并集"。文档只确认请求语法与并集语义，
  不确认集合等价。`scheme.md` §6 与 §12 要求不得把未知当作已覆盖——这里的"未知"是文档层面的未知。
- **没有**任何一句描述多关键词与 `scope`/`tag`/`filter`/`radius` 的交互。
- **没有**给出 `page_num` 的上限；能翻多远只由 F3/F4 的 150 条封顶间接决定（`page_size=20` 时约 8 页，
  恰好等于现有 `MAX_PAGES = 8`）。

### 3.2 官方 v3 文档本身未能取得（重要）

`scheme.md` §15 引用的 v3 文档地址是一个纯 JS 单页应用，抓取只能得到标题壳，正文为空。
因此上面的事实来自**官方 v2 文档原文**，并由若干第三方镜像转载的 v3 参数表交叉印证。
这是一处真实的证据缺口：**任何 v3 专属差异都不能用本文件断定**。

**由此产生一个必须先澄清的风险**：有第三方镜像把 v3 圆形检索的服务地址写作
`https://api.map.baidu.com/place/v3/search`，而本仓库发送的是 `https://api.map.baidu.com/place/v3/around`
（`app/baidu.py::API_PATH`，并被 `tests/test_poi_provider.py` 固定）。
两者**未经官方文档确认哪一个正确**。本审计不修改它（改生产请求路径属于独立授权范围），
但把它登记为"真实对照开始前必须由运营者用官方文档确认"的前置项（§7 P3）。

## 4. 归属审计：并集页能把结果分回原关键词吗

**分两层看，结论不同——这是本审计最容易被误读的地方。**

### 4.1 关键词层：不能

官方响应结构（v2 全表及 v3 镜像新增字段）中**没有任何字段**说明某条 POI 命中了提交的哪个关键词。
`tag` / `type` / `classified_poi_tag` 表达的是 POI 自身的分类，不是调用方提交的词。
（百度另有一个"多维检索"接口文档了 `matched_terms` 之类的匹配标签，但那是**另一个端点**，
不能当作 place v3 的字段。）

更严格地说，本仓库还多一层损失：`app/poi/provider.py::whitelist()` 只放行
`status`/`total`/`result_type`/`results[uid,name,address,location,detail_info{classified_poi_tag,parent_id,navi_location}]`。
`tag`、`type`、`detail` 等字段即使服务返回，也**不会跨越传输边界**。
所以"用服务返回的分类字段反推关键词"这条路在本仓库里连数据都拿不到。

**结论**：若无法追溯来源，就不能凭一次混合查询给参与合并的关键词标记"已覆盖"
（`scheme.md` §6 C3 第一条）。这一条是硬约束。

### 4.2 小类层：分类不依赖查询

但**类别归属**在本仓库里并不是由"哪条查询取回来的"决定的：
`normalize.classify(name, tags)` 只看设施自己的名称与分类标签。因此：

- 合并**不会**让设施的类别归属变错——回收的行仍按同一套词典判类；
- 真正被破坏的是**完整性证据**：`OnlinePlanner._covered(block, category, query)` 以
  （块, 小类, 关键词）为键记录"这个词在这个块上查完了"。一个并集页无法对其中任一关键词
  作出这个断言。

**这直接给出合并粒度的正确选择**：把**同一个小类的全部关键词**作为合并单位时，
（块, 小类）层面的覆盖仍然可以被完整地定义——损失只在于"这个设施是被哪个同义词找到的"，
而小类才是报告与评分使用的单位。反之，把不同小类的关键词装进一个查询，就同时毁掉了两个小类的
完整性断言。

## 5. 分页与截断审计：两条会直接吃掉收益的机制

### 5.1 硬阻塞：现有校验器会拒收并集页

F2 说明并集页的记录数是 `关键词个数 × page_size`。本仓库发送 `page_size=20`，于是在 k≥2 时
单页可能返回 40 / 60 / … 条。而 `app/place_protocol.py::response_error()` 的第 34 行是：

```python
if not isinstance(payload.get("results"), list) or len(payload["results"]) > 20:
    return "invalid_response"
```

即**超过 20 条即判为 `invalid_response`，整页作废、按失败记账**。
这不是理论风险：k=2 的并集查询按文档就会返回约 40 条。

**结论**：任何合并方案在进入真实对照之前，必须先决定并集页的读取规则
（放宽校验器 / 改用更小的 `page_size` / 其它），并且这一改动本身需要独立评审。
在此之前，"合并查询"在本仓库中**不可试验**——这是 §7 的 P1 阻塞项。

### 5.2 拥挤截断：合并会更容易触发细分，反而多花钱

- F3：`total` 最多 150。k 个关键词的并集 `total` 天然是各自之和的量级，**更快撞到 150**。
- `Pagination` 把 `total >= 150` 记为 `possible_truncation`；该值属于
  `online.DENSITY_SIGNALS`，会触发 `_subdivide()`，把一个块拆成 4 个子块、各再查一次。

于是出现 `scheme.md` §12 点名的那种反例：**首轮关键词组数变少，但因为更容易截断而触发细分，
整轮网络调用反而增加**。这不是猜测，是两条既有规则的直接推论；C2 必须按"整轮成本"比较，
而不是只数首轮请求。

### 5.3 同页重复 UID

一个设施可能同时命中并集里的多个关键词，此时它在**同一页内只应出现一次**（并集语义），
但文档没有说明跨页去重规则。现有 `Pagination` 会把"页码>1 时出现重复 UID"判为
`pagination_anomaly`（同样触发细分）。合并放大了同一 UID 匹配多个关键词的概率，
即放大了触发 `pagination_anomaly` 的概率。离线夹具必须覆盖这一分支（C2 已列）。

## 6. 候选分组与保守回退

按风险从低到高。**"可试验"不等于"可上线"**：下表只说明哪一组值得进 C2 的离线对照。

| 粒度 | 例 | 关键词数 | 类别完整性 | 归属损失 | 判定 |
| --- | --- | --- | --- | --- | --- |
| 小类内同义词组 | `药店$药房`、`养老院$敬老院$养老服务中心` | 2–4 | 可定义（以（块,小类）为单位） | 只丢"哪个同义词命中" | **可试验（首选）** |
| 同大类内多个小类 | `菜市场$生鲜$超市` | 3–11 | 丢失（无法再断言各小类各自查完） | 小类级完整性不可证 | 需先定义"整类合并即整类覆盖"的产品口径，否则不可 |
| 跨大类机械装箱 | `药店$超市$小学$银行…` | ≤10 | 全部丢失 | 大量关键词的完整性不可证 | **不可采用**（`scheme.md` §12 明确禁止） |

**回退规则**（写入 C2 的候选实现）：

1. 一个组只有在**同属一个小类**时才允许合并；否则保持独立查询。
2. 合并页只能把证据记在该小类的"合并身份"下；参与合并的**单个关键词**一律记为
   `unknown/incomplete`，不得标 `completed`。
3. 需要逐关键词结论时，追加一次该关键词的独立查询（消耗真实额度，必须计入整轮成本）。
4. 命中 `possible_truncation` / `page_limit` / `pagination_anomaly` / `pagination_uncertain`
   时不得因为"合并省了首轮"而放松既有细分与有界重试。

## 7. 与既有机制的兼容性

| 机制 | 兼容性判定 | 依据 |
| --- | --- | --- |
| `coarse_blocks`（2×2 粗分块） | 兼容。合并只改"一个块内发几个查询"，不改分块 | `online.coarse_blocks` |
| 细分 `_subdivide` | 兼容但**会被更频繁触发**（§5.2） | `DENSE_SIGNALS` |
| 有界重试 `MAX_PAGE_ATTEMPTS=2` | 必须原样保留 | `online.RETRYABLE` |
| 缓存键 | **必须换命名空间**。键由 `page_key(...provider, apiVersion)` 组成，合并计划的语义不同，绝不可与独立查询共用页面缓存 | `cache.COMPONENTS['page']`、`poi/cache.page_key` |
| 计划版本 | 需要独立 `planVersion`（C3 要求）。本项目用 `provider`/`apiVersion` 身份隔离，因此候选臂应声明自己的身份串，生产键不动 | 同上 |
| 唯一扣费入口 | 必须继续只经 `ServicePool.attempt()`；合并 runner 不得自建第二套记账 | `quota.ServicePool.attempt` |
| 评分来源字段 | 合并不改变评分定义。评分输入是设施证据集合，而类别归属仍由 `classify` 决定（§4.2），因此**设施集合不变则分数不应变化** | `checkups/accessibility_stage.py` |
| 补查身份 `extension_identity` | 不受影响：补查仍按客户端的类别集合 + 预算判定 | `checkups/manager.py` |
| `training` 等 `negative` 小类 | 不受影响，但覆盖表必须标注其 0 是词典决定 | §2 |

## 9. 结论

- 官方文档确认 `$` 并集语法（≤10 词），但**从未**承诺"并集 = 分别查询的集合等价"。
- 并集页**无法**把单条 POI 归属回某个关键词；本仓库的响应白名单更进一步使这类字段不可得。
  因此**逐关键词的覆盖断言在合并后不成立**。
- 类别归属不受影响（`classify` 只看名称与标签），所以**同小类内合并**是唯一在语义上站得住的粒度。
- 两条既有机制会吃掉甚至反转收益：**`>20` 条即判无效**（硬阻塞）、**`total≥150` 触发细分**
  （拥挤反例）。二者都属于"我们必须先处理/先测量"的问题，而不是"合并带来的好处"。
