### 1.1 第 8、9 项为什么重要（不是排版问题）

`Settings` 配了 `extra="ignore"`，所以**拼错的键不会报错**，那一行只是静默失效：
`ANALYSIS_PROVIDE` 失效时 `analysis_provider` 落到默认 `baidu`（今天恰好无害），
但如果有人**打算**用它切到 `synthetic` 离线模式，实际会**照常走真实 provider**。
`OSM_*` 那三个键同理：它们看起来像配置，实际什么也没做。

这三行目前都无害，但"以为切了其实没切"正是本项目"不伪造、不误发"要防的一类问题。
**`.env` 未被提交**（`.gitignore`），修正只发生在本机；`.env.example` 一直是正确拼写，
所以问题只在运营者本地文件里。**未读、未打印任何值。**

### 4.1 未解决的差异：流量图与账本对不上（**真实实验前的阻塞项**）

**运营者报告**：控制台流量图与应用账本对不上；并推测仓库里的 `/place/v3/around`
"可能是其他协作者误上传的"（即端点可能不对）。

**本地反证（E1，全部来自已落盘的修订，未发起任何新请求）**：

| 观察 | 数值 |
| --- | --- |
| 带真实 provider 身份的修订 | **30** 个：`provider=baidu_place`、`apiVersion=3.0`、`dataSource=baidu_place`（21 completed / 5 partial / 4 failed） |
| 成功解析的页数 | **776** 页，页面自带上游 `total`（3–18 等） |

| 未成功的页 | **20** 页，原因**全部**是额度层拒绝（`daily_budget_exhausted` 6、`task_budget_exhausted` 14），**没有一页是上游拒绝** |
| 修订 mtime 与账本日期 | 完全对应：09-29(15)、09-30(3)、10-02(4)、10-04(6)、10-05(1)、10-08(1) |

**结论**：`/place/v3/around` **确实返回过真实数据**——776 个成功的真实页、217 个真实 GUID 设施。
一个写错的路径不可能产生这些。因此"端点写错"这一推测**与本地证据冲突**，**不应据此改动生产请求路径**。
（第三方镜像声称 v3 是 `/place/v3/search` 的那条差异仍未核实，见 `08` §3.2；但它现在既不被证实、也不被需要。）

**更可能的解释，按可能性排序**（都需要控制台的数字才能定论）：

1. **AK 不是同一个**：应用配置的 AK 与控制台页面对应的 AK 可能不同。这是"账本有量、控制台无量"最直接的解释。
2. **控制台只统计被计费的调用**：若某些调用被上游拒绝，控制台可能不计。
   但本地记录里**没有上游拒绝的页**，所以这条只解释 4 个 `failed` 修订（它们连请求都没发出去）。
3. **日期口径不同**：流量图的时间粒度/时区与账本的北京时间跨日不一致。
4. **比对的具体日期不是 10-08**：账本对 10-08 记的是 **60**，对 09-29 记的是 **406**。

**需要控制台提供的确切数字**（这样差异就能一次定死，而不用再猜）：

- 地点检索在 **2026-10-08** 的当日调用数（账本=**60**）；
- 地点检索在 **2026-09-29** 的当日调用数（账本=**406**）；
- 控制台页面对应的**是哪个 AK**（只要说明"与 `.env` 里的是同一个 / 不是"，**不要给出 AK 值**）；
- 流量图的时间粒度（按日？时区？）。

**在拿到这四条之前，真实对照实验不开始**：如果端点是错的，实验会白花调用；
如果端点是好的而 AK 不同，实验会记到另一个账号上。两种都不该在不清楚的情况下花额度。
